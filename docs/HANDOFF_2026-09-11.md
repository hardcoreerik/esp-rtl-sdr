Written for a fresh AI/engineer with zero prior context. Read this before touching

## Takeover update — matched-IF repair (supersedes the older tuning diagnosis below)

The older notes below are retained as investigation history, but their statement
that V3c had not received FM is no longer current. After the PLL-only commit
`ff1f07c`, the real V3c received known stations and matching RDS, but every
station appeared roughly 1.76 MHz low on the OrcSDR dial: 96.1 MHz KEZL near
94.33 MHz and 99.1 MHz The Beat near 97.33 MHz.

This was not an OrcSDR display or RDS-staleness bug. The driver had configured
the two sides of the tuner/demodulator IF pair differently:

- Blog V3 tuner PLL: 3,570,000 Hz after `ff1f07c`.
- RTL2832 demodulator after the shared full init table: approximately
  1,814,972 Hz, the existing Blog V4 value.
- Difference: `3,570,000 - 1,814,972 = 1,755,028 Hz`.

That exact mismatch accounts for the observed station displacement, with the
remaining dial approximation explained by the existing FM auto-centering range.
OrcSDR was displaying its requested RF frequency correctly; the tuner and demod
were interpreting that request around different IF centers.

### Implemented local repair

Blog V3 initialization now replays the already-captured RTL2832 standard-IF
slice immediately after sample-rate programming and before the first PLL tune:

1. write demod register `0x19 = 0x38`, then its captured settle read;
2. write demod register `0x1A = 0x11`, then its captured settle read;
3. write demod register `0x1B = 0x12`, then its captured settle read.

These are existing records `kRtlInitTransfers[98..103]`; no new register values
were invented. Their source is the first-party official-driver capture at
`docs/captures/v3c_official_driver_control_transfers_2026-09-11.txt`, frames
11816 through 11826. The restore is gated only to `BlogV3`. Blog V4 executes no
new USB transfers and keeps its measured matched 1.814972 MHz path. Nooelec is
unchanged because no physical evidence supports assigning it the V3c IF.

Hot retunes deliberately do not rewrite the demod IF. Each initialization/new
stream start establishes the matched pair once, then the existing hot-retune
path changes only the PLL as before. The tune log now appends `pll_if_hz`, and
the restore emits one milestone with profile, PLL IF, demod IF, applied state,
and record count.

## TL;DR — where things stand right now

- The crash/reboot-loop that started this investigation (plugging a real RTL-SDR
  Blog "V3c" dongle into a Tab5 running OrcSDR crashed the device a few seconds
  after boot) is **fixed and verified on real hardware**, across dozens of
  hot-plug/cold-boot cycles.
- Device identification, USB enumeration, and streaming (IQ samples flowing over
  USB, no crashes) all work reliably on V3c now.
- Manual RF gain control for V3c was just wired up tonight (two commits, not yet
  pushed) but **has not produced usable FM reception on real hardware yet** — last
  test was "just static" / "no indication of signal" on 96.1 FM (KEZL, the
  project's standard FM test station).
- **New, unresolved, and possibly more important than gain calibration**: while
  testing just now, `RTL_DRIVER STATUS` polled three times over about a minute
  showed `state=STREAMING` but `bytes=74645504 blocks=2278` **frozen identical**
  across all three polls. Either the USB bulk stream is actually stalled while
  still reporting itself as healthy, or the metrics counters themselves aren't
  updating. This needs to be root-caused before spending more time on gain
  register values — a stalled stream would produce exactly the symptom
  ("static", "no indication of signal") regardless of gain correctness.

## The actual crash fix (verified, high confidence)

Root cause: `probe_blog_v3_tuner()` was running an R820T2 chip-ID probe **before**
the RTL2832U demodulator's own bring-up sequence had run. On real V3c hardware
this produced an EP0 STALL that the ESP-IDF USB Host stack's assertion couldn't
recover from, crashing the device. This was misdiagnosed earlier in the
investigation as "a stock ESP-IDF usb_host bug, unfixable at the application
level" — that conclusion was wrong and has been corrected in this repo's
`CHANGELOG.md`/`TROUBLESHOOTING.md`.

Fix (already committed, well before tonight, commit `b74ddde`): a new
`run_demod_bringup()` function replays the first 86 records of
`kRtlInitTransfers` before any tuner probe runs. Commit `440f45d` also added a
belt-and-suspenders USB enumeration fault guard using `RTC_NOINIT_ATTR` to detect
and recover from a crash-loop across resets, independent of the real fix.

This part is solid — do not re-litigate it without new hardware evidence.

## Tonight's work: manual gain for V3c/R820T2

### What changed (2 commits on `codex/usb-enum-fault-guard`, HEAD = `3fe9de8`)

1. **`8291e40`** — `feat: interpolated manual gain for BlogV3/R820T2`
   - New file `private/interpolated_gain_r820t2.hpp`: a 29-point gain table
     (`kR820T2InterpolatedGainSteps[]`) for the R820T2/R860 tuner (used on V3/V3c),
     covering 0.0–49.6 dB in the same 29 steps the official rtl-sdr driver
     advertises. **Only two of the 29 points are independently
     hardware-confirmed** (see below); the other 27 are linearly interpolated
     between them. This is explicitly documented as an estimate in the header
     comment — do not describe intermediate values as "measured."
   - New function `apply_r820t2_gain_records()` in `src/esp_rtl_sdr.cpp`: writes
     reg05 (LNA gain) and reg07 (mixer gain) directly via the existing
     `run_record()`/`measured_v4_ir_reg_write()` machinery, bypassing V4's
     `run_band_frontend()` (which does V4-specific triplexer/GPIO input routing
     that doesn't apply to V3c's single-input board).
   - `apply_gain_records()` now branches at the top: R820T2-family profiles
     (`rtl_profile_uses_r820t2_i2c_remap()` — true for `BlogV3` and
     `NooelecSmartV5`) go through the new function; V4 keeps its existing path
     unchanged.
   - `private/rtl_profile.hpp`: `BlogV3` now gets its own case in
     `rtl_profile_device_capabilities()` including `ESP_RTL_SDR_CAP_GAIN`
     (previously it shared a case with `NooelecSmartV5` and neither had this
     capability). `NooelecSmartV5` deliberately still does **not** get
     `CAP_GAIN` — it's never been tested.

2. **`3fe9de8`** — `fix: also write reg0x0c in R820T2 manual gain path`
   - V4's gain path (`run_band_frontend()`) always writes reg0x0c alongside
     reg05/reg07 — `kMeasuredV4GainReg0c = 0x68`, measured constant across V4's
     *entire* gain ladder (see `private/measured_gain_bias_v4.hpp`). The first
     cut of `apply_r820t2_gain_records()` only wrote reg05/reg07 and never
     touched reg0x0c at all, leaving it at whatever `run_demod_bringup()`/tuner
     init last set. Register 0x0c is very likely a separate VGA/IF gain stage —
     omitting it would silently cap real gain regardless of reg05/07.
   - Fix: `apply_r820t2_gain_records()` now also writes reg0x0c using the same
     `kMeasuredV4GainReg0c` value V4 uses. **This is a borrowed value, not an
     independently measured R820T2 value.** Rationale: R828D (V4's tuner) and
     R820T2/R860 (V3c's tuner) are both Rafael Micro R82xx-family parts, so
     sharing a register value across them is a reasonable first attempt, but it
     has not been verified to be correct for R820T2 specifically.
   - Rebuilt and flashed to the real Tab5. Result: **still just static / no
     indication of signal** — this fix alone did not solve reception. See the
     stalled-stream lead above, which may be the actual blocker.

### The two real hardware anchors (high confidence, these ARE independently verified)

From `private/interpolated_gain_r820t2.hpp`:

- **0.0 dB → reg05=0x90, reg07=0x60** — the observed default/idle state on every
  real V3c and Blog V4 session immediately after tuner init, before any gain
  change is requested.
- **49.6 dB → reg05=0x9f, reg07=0x6e** — captured from the *official* RTL-SDR
  Blog Windows driver (`rtl_sdr.exe -g 49.6`), a single continuous session,
  confirmed settled and held with **zero further register writes for 4+
  minutes**. This is the one fully unambiguous data point from the whole
  investigation.

Everything in between is interpolated by `(requested dB) / 49.6` fraction. Full
evidence trail, including multiple failed attempts to capture the real 29-step
ladder independently, is in `docs/captures/NOTES.md` in this repo.

### Known gaps / things NOT done

- `esp_rtl_sdr_get_tuner_gains()` (src/esp_rtl_sdr.cpp:3948) is **hardcoded** to
  always report `kMeasuredV4GainSteps`/`kMeasuredV4GainStepCount` (V4's table)
  regardless of the connected profile — it does not branch on
  `rtl_profile_uses_r820t2_i2c_remap()` the way `apply_gain_records()` does.
  Right now this happens to be harmless for V3c because both tables use the same
  29 `tenth_db` values (0, 9, 14, 27, ... 496) even though the actual register
  values differ — the UI queries this function only to get the *list of
  selectable dB values*, then calls `esp_rtl_sdr_set_tuner_gain(tenth_db)`,
  which does correctly route through `apply_gain_records()` → the R820T2 path.
  But it's semantically wrong and worth fixing for correctness/future-proofing
  if the two tables' `tenth_db` values ever diverge.
- The 27 interpolated points have never been independently verified — multiple
  attempts this session (SDR# UI slider sweep, per-invocation `rtl_sdr.exe -g X`
  runs, a persistent single-session Python/ctypes sweep holding 30s per step)
  all produced register drift that didn't correlate cleanly with a simple
  settle-per-step model. See `docs/captures/NOTES.md` for the raw data
  (`v3c_gain_table_28step_10s_2026-09-11.txt` and friends).
- `RTL_DRIVER GAIN`/`GAINMODE`/`RTLAGC`/`BIAS` console commands require a full
  HMAC-SHA256 challenge/response pairing (`AUTH <nonce_hex> <proof_hex>` at
  `ui/main.cpp:14638`) — we do not have the device's pairing key, so these
  cannot be scripted from serial. Only the plain `RTL_DRIVER STATUS` read
  bypasses this gate. **All manual-gain testing has to go through the
  touchscreen UI directly on the device.**

## The stalled-stream lead (discovered just now, NOT yet investigated)

Three `RTL_DRIVER STATUS` polls over roughly 70 seconds, with the device sitting
on the FM screen with V3c plugged in:

```
bytes=74645504 blocks=2278 effective_sps=959947 overruns=0 drops=0 shadow_ok=1 metrics_ok=1
bytes=74645504 blocks=2278 effective_sps=959947 overruns=0 drops=0 shadow_ok=1 metrics_ok=1
bytes=74645504 blocks=2278 effective_sps=959947 overruns=0 drops=0 shadow_ok=1 metrics_ok=1
```

Identical byte/block counts across all three, while `state=STREAMING` the whole
time and zero overruns/drops reported. This was NOT chased down further tonight
— it might be:
- a genuinely stalled USB bulk transfer loop (would fully explain "just static"
  independent of gain correctness — recommend checking this **before** doing any
  more gain-table work),
- a metrics/counter update bug unrelated to the actual data path (i.e. audio and
  spectrum ARE flowing, only the STATUS counters are stale), or
- an artifact of how/when the FM screen requests fresh callback delivery vs. how
  `RTL_DRIVER STATUS` reads the shadow state.

**Recommended next step for whoever picks this up**: before touching gain
registers again, confirm whether the byte/block counters are truly frozen (poll
`RTL_DRIVER STATUS` a few more times, 5-10s apart, while actively on the FM
screen) and whether that correlates with actually-frozen audio/spectrum on
screen. If the stream is genuinely stalled, that's the real bug and gain
calibration work should pause until it's fixed.

# 2. Activate ESP-IDF and build
$env:IDF_PATH = "C:\Espressif\frameworks\esp-idf-v5.5.4"

lowered from 40960 to 24576 — this is an unrelated, pre-existing memory-margin
issue on current HEAD (`Could not reserve internal/DMA pool` at boot otherwise),
not something to "fix" as part of this work, just a local build requirement.
