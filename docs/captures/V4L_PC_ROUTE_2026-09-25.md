# Blog V4L / V4 / V3c PC measurements (2026-09-25 local)

This is a first-party, hardware-observed PC test report for the particular
three dongles the user connected. It records vendor-driver USB control
transfers, user-performed no-load SMA voltage checks, and bounded off-air IQ
and AM-audio captures. The objective was to learn what a PC driver actually
programs before changing `esp-rtl-sdr`; this report does **not** establish
effective RF gain in dB, analog filter passband, loaded bias-tee capacity,
or OrcSDR/Tab5 acceptance. Vendor V4L product description:
<https://www.rtl-sdr.com/v4l/>. Programming observations below were derived
from these USB traces, not copied from vendor or open-source driver code.

## Control-test procedure and decoding

USBPcap recorded the selected PC USB controller while the vendor x64
`rtlsdr.dll` API or its bundled CLI issued bounded requests. TShark decoded
host-to-device vendor control **Setup** transfers. For R828S/R820T-family
I2C writes, `wValue=0x0034`, `wIndex=0x0610`; the first byte of
`usb.data_fragment` is a tuner register address, followed by one or more
data bytes. Blog V4/R828D instead uses its measured `wValue=0x0074` path.
GPIO writes were decoded independently from vendor control writes to
`wValue=0x3004`, `0x3003`, and `0x3001` with `wIndex=0x0210`. A command's
**settled** register state was taken after its setup and retune sequence,
excluding earlier initialization, transient values, and device-close
writes. PLL LO values were decoded from each settled tuner divider block
and cross-checked against the requested RF plus the demod IF. This is why
the route conclusions use PLL, GPIO, and input/filter registers together.

Read-only inspection example (replace the filename with the raw capture):

```powershell
& 'C:\Program Files\Wireshark\tshark.exe' `
  -r 'C:\Tools\esp-rtl-sdr-lab\captures\v4l-route-boundaries-20260925.pcapng' `
  -Y 'usb.setup.wValue == 0x0034 && usb.endpoint_address.direction == 0' `
  -T fields -e frame.time_relative -e usb.setup.wIndex -e usb.data_fragment
```

## FM / HF / FM route at fixed 2.4 MS/s

The vendor driver returned from 96.1 MHz FM to 1.280 MHz AM and back to FM
without a device re-open. USB I2C writes use RTL2832 vendor OUT `wValue=0x0034`,
`wIndex=0x0610` to reach the R828S. The visible route transitions were:

| Requested RF | Tuned R828S route | GPIO writes (`0x3004/03/01`) | Settled tuner clues |
|---|---|---|---|
| 96.1 MHz FM | Native VHF | `06/39/38` | `17=20`, `1b=34`, `05=83` (auto gain) |
| 1.280 MHz AM | HF upconverter | `06/39/18` | `17=28`, `1b=df` then `00`, `05=e3` (auto gain) |
| 96.1 MHz FM | Native VHF | `06/39/38` | returns to `17=20`, `1b=34`, `05=83` |

The PLL bytes resolve the RF path more strongly than the GPIO labels alone.
At FM, settled `10=84,14=4a,16=65,15=b0` decodes to LO
**97,914,990 Hz**, or RF + **1,814,990 Hz**. At AM, settled
`10=a4,14=85,16=70,15=5a` decodes to LO **31,894,986 Hz**, or
1,280,000 + 28,800,000 + **1,814,986 Hz**. Thus the PC route uses the
vendor-described **28.8 MHz HF upconverter**, then the same approximately
**1.815 MHz tuner IF offset**. The ~10-20 Hz residual is PLL quantization,
not a different IF. The corresponding demod IF register triple on the default
2.4 MS/s setup is `19/1a/1b = 3b/f7/78`, which decodes to about
**1,814,996 Hz** using the 28.8 MHz reference and signed 22-bit IF encoding.
The IF triple did not change merely when retuning FM→AM→FM at fixed bandwidth.

The USB chronology matters for firmware. In the same-session capture,
the later AM retune began near 2.304 s with R828S writes `17=28`,
`1a=2a`, `1b=df`, then its PLL writes. After the PLL sequence, the driver
wrote `1a=68`, `1b=00`, GPIO `3004=06`, `3003=39`, `3001=18`, then
`05=c3` followed by settled `05=e3`. The next FM retune began near
3.319 s with `17=20`, `1a=2a`, `1b=34`, then PLL writes; after those it
wrote GPIO `3004=06`, `3003=39`, `3001=38` and `05=a3` followed by
settled `05=83`. These are representative observed **before-PLL and
after-PLL phases**, not one contiguous front-end register block. No new
`06` write appeared in those hot AM/FM phases; `06=30` was seen during
earlier initialization. That is another reason not to transplant V4's
reg-06 triplexer plan into V4L. All tuner bytes here are on `0x0034`.

V4L's R828S I2C address path is the V3-style `0x0034`; it is **not** the Blog
V4/R828D `0x0074` path. V4L's RF route also differs from V4's triplexer:
the measured V4L HF and VHF GPIO values happen to match V4's `18/38`, but
the input-register values do not. Reusing the entire V4 front-end table would
conflate two different boards. Likewise, V3c's direct-Q HF route is not a
valid substitute for V4L's upconverter.

## Hardware tuner bandwidth and IF coupling

With center RF held at 96.1 MHz and sample rate held at 2.4 MS/s, each
`rtlsdr_set_tuner_bandwidth` call returned 0. The driver wrote tuner filter
registers `0a/0b`, retuned the PLL, and changed the RTL2832 demod IF to match.
This is a tuner-bandwidth control, distinct from the IQ sample rate or SDR#'s
post-IQ software filter. Values below are the settled writes after each call.

| Requested tuner BW | R828S `0a/0b` | Demod `19/1a/1b` | Decoded demod IF | Decoded PLL IF |
|---:|---|---|---:|---:|
| 0 (automatic) | `c4/8f` | `3b/f7/78` | 1,814,996 Hz | 1,814,990 Hz |
| 200 kHz | `c4/e6` | `3b/47/1d` | 2,124,996 Hz | 2,124,970 Hz |
| 300 kHz | `c4/e6` | `3b/47/1d` | 2,124,996 Hz | 2,124,970 Hz |
| 500 kHz | `c4/e8` | `3b/80/00` | 2,025,000 Hz | 2,024,994 Hz |
| 1,000 kHz | `c4/eb` | `3c/38/e4` | 1,699,997 Hz | 1,700,018 Hz |
| 1,800 kHz | `c4/ac` | `3c/1c/72` | 1,749,999 Hz | 1,750,006 Hz |
| 2,400 kHz | `c4/8f` | `3b/f7/78` | 1,814,996 Hz | 1,814,990 Hz |

These values prove command acceptance and matched USB programming, not the
actual analog -3 dB passbands. In particular, 200 and 300 kHz quantize to the
same setting. Any firmware tuner-bandwidth API must update **both** PLL and
demod IF together; changing `0b` alone would move the received spectrum.

The same seven-request control-only sweep was repeated on the Blog V4/R828D
with its antenna disconnected. All API calls returned 0. V4 used `0a=c5`
where V4L used `0a=c4`; `0b`, the demod IF triple, and the settled PLL bytes
matched the V4L rows exactly at every requested width. Thus the shared IF and
bandwidth choices are PC-trace-confirmed for **both** boards, but their tuner
filter register `0a` must stay board-specific. Neither trace measures the
actual RF passband.

The same seven-request sweep was then captured on the user-identified V3c,
which exposes a bare `Realtek / RTL2838UHIDIR` descriptor and an R820T-family
tuner to the PC driver. All API calls returned 0. After the driver briefly
entered and left direct-sampling mode during setup, the settled **96.1 MHz**
bandwidth writes matched V4 byte-for-byte: `0a=c5`, the same `0b` settings,
the same demod IF triples, and the same PLL bytes at each requested width.
This PC driver used ~1.815 MHz for automatic/2.4 MHz bandwidth on this V3c
session. That is not a contradiction of the separate OrcSDR V3c hardware
measurement of a matched 3.570 MHz IF under its own initialization path;
the IF must be interpreted together with its paired PLL and demod settings.
No actual analog passband was measured on any of the three boards.
